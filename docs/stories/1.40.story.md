# Story 1.40 — E2E Real: Troca de Chaves ECDH por Sessão

## Status: Ready for Review

## Story

Como usuário, quero que minhas mensagens sejam protegidas por criptografia ponta-a-ponta real, onde nem o servidor nem qualquer observador de rede consiga decifrá-las, mesmo conhecendo o slug da sala.

## Contexto Técnico

### Problema com a Implementação Atual

`deriveRoomKey(roomId)` em `src/lib/crypto.ts` deriva a chave AES-256 deterministicamente do slug público da sala via PBKDF2. Qualquer pessoa que conheça o slug pode derivar a mesma chave e decifrar todas as mensagens — incluindo um servidor comprometido ou observador de rede que capture o slug da URL.

### Solução: ECDH por Sessão + Chave de Sala Distribuída

Cada cliente gera um par de chaves **X25519 por sessão** (em memória, nunca enviada ao servidor). Ao entrar numa sala, clientes trocam chaves públicas via servidor. O primeiro participante gera uma chave AES-256 aleatória para a sala e a distribui cifrada com a chave pública de cada novo participante (ECDH). O servidor nunca vê a chave da sala em plaintext.

```
Cliente A                    Servidor                    Cliente B
  |                             |                             |
  |-- pubKey(A) → join-room --> |                             |
  |                             | <-- pubKey(B) + join-room --|
  |                             |-- pubKey(A) → key-exchange -|
  |<-- pubKey(B) + key-exchange-|                             |
  |                             |                             |
  | [A gera roomKey aleatória]  |                             |
  |                             |                             |
  | roomKey cifrada com pubKey(B) → room-key-offer ---------->|
  |                             |                             |
  |                     [B decifra roomKey com privKey(B)]    |
  |                             |                             |
  |<==== mensagens AES-GCM com roomKey compartilhada ======>  |
```

### Impacto em Usuários Existentes

- **Mensagens**: não persistidas no banco — zero perda
- **Imagens no disco**: ficam ilegíveis (cifradas com chave antiga) — somem com TTL natural
- **Ação necessária pelo usuário**: nenhuma — transparente no reconect
- **Multi-device**: chave é por sessão (in-memory) — sem histórico entre abas/dispositivos (alinhado com branding "incógnito")

### Arquitetura de Chaves

```
Por sessão (in-memory):
  privKey  ←  crypto.subtle.generateKey('X25519', extractable=false)
  pubKey   →  exportado como ArrayBuffer → base64 → enviado ao servidor

Por sala (in-memory, nunca persiste):
  roomKey  ←  primeiro participante: crypto.getRandomValues(32 bytes) → importar como AES-GCM
  roomKey  ←  demais participantes: ECDH(privKey, pubKey(outro)) → derivar → decifrar envelope
```

### Protocolo de Troca (Socket.IO Events)

| Evento (cliente→servidor) | Payload | Descrição |
|--------------------------|---------|-----------|
| `key-exchange` | `{ roomId, pubKey: string }` | Cliente anuncia chave pública ao entrar na sala |
| `room-key-offer` | `{ roomId, targetSocketId, encryptedRoomKey: string, iv: string, senderPubKey: string }` | Distribui roomKey cifrada para novo participante |

| Evento (servidor→cliente) | Payload | Descrição |
|--------------------------|---------|-----------|
| `peer-pubkey` | `{ socketId, pubKey: string }` | Relay da chave pública de outro participante |
| `room-key-offer` | `{ encryptedRoomKey: string, iv: string, senderPubKey: string }` | Relay do envelope cifrado para o destinatário |

### Fluxo de Entrada na Sala

1. Cliente gera keypair X25519 (se ainda não tiver na sessão)
2. Emite `key-exchange` com roomId + pubKey(base64)
3. Servidor relaya `peer-pubkey` para todos na sala e envia de volta as pubKeys já presentes
4. **Se for o primeiro na sala**: gera `roomKey` aleatória (AES-256), armazena em memória
5. **Se não for o primeiro**: aguarda `room-key-offer` de qualquer participante existente
6. Participantes existentes recebem `peer-pubkey` do novo → derivam shared secret via ECDH → cifram `roomKey` com esse secret → emitem `room-key-offer` ao novo participante
7. Novo participante recebe `room-key-offer` → ECDH(privKey, senderPubKey) → decifra `roomKey`
8. A partir daqui, todas as mensagens usam `roomKey` via AES-GCM (mesmo formato atual)

### O que NÃO muda

- Formato das mensagens cifradas (`{ ciphertext, iv }`) — igual ao atual
- Funções `encryptMessage`, `decryptMessage`, `encryptBinary`, `decryptBinary` em `crypto.ts`
- Lógica do servidor de relay de mensagens (`send-message`, `receive-message`)
- UI completa — sem mudança nenhuma para o usuário

## Acceptance Criteria

### Geração e Troca de Chaves

- [ ] AC1: Ao entrar numa sala, cliente gera keypair X25519 (se não existir na sessão) e emite `key-exchange` com a pubKey em base64
- [ ] AC2: Servidor relaya `peer-pubkey` para todos os participantes existentes e envia de volta as pubKeys dos participantes para o novo entrante
- [ ] AC3: O primeiro participante de uma sala gera `roomKey` aleatória (AES-256 via `crypto.getRandomValues`) — sem depender do roomId
- [ ] AC4: Quando novo participante entra, os participantes existentes emitem `room-key-offer` com `roomKey` cifrada via ECDH + AES-GCM para o novo

### Decifração e Uso da Room Key

- [ ] AC5: Novo participante recebe `room-key-offer`, deriva shared secret via ECDH com `senderPubKey`, decifra a `roomKey` e a armazena em memória
- [ ] AC6: Após receber a `roomKey`, participante consegue decifrar mensagens recebidas e cifrar mensagens enviadas normalmente
- [ ] AC7: Primeiro participante (que gerou a `roomKey`) consegue enviar e receber mensagens imediatamente, sem aguardar oferta

### Isolamento e Segurança

- [ ] AC8: `deriveRoomKey(roomId)` é removida de `crypto.ts` (ou marcada como deprecated e não usada)
- [ ] AC9: A chave privada X25519 nunca é serializada ou enviada ao servidor
- [ ] AC10: Sala com apenas 1 participante: consegue enviar mensagens (mesmo sem outros — criptografa com a própria roomKey gerada)
- [ ] AC11: Novo participante que entra depois de mensagens já trocadas: não consegue decifrar mensagens antigas (forward secrecy por sessão) — isso é comportamento esperado e correto

### Compatibilidade e Fallback

- [ ] AC12: Se `room-key-offer` demorar mais de 5 segundos (ex: única pessoa na sala), cliente gera própria `roomKey` e começa a operar — sem tela de espera indefinida
- [ ] AC13: Mensagens enviadas antes da `roomKey` estar disponível são enfileiradas e enviadas após a chave ser estabelecida (não são perdidas silenciosamente)

### Sem Regressão

- [ ] AC14: `encryptMessage`, `decryptMessage`, `encryptBinary`, `decryptBinary` em `crypto.ts` continuam funcionando identicamente — apenas a fonte da `CryptoKey` muda
- [ ] AC15: Imagens cifradas e enviadas continuam funcionando com o novo esquema
- [ ] AC16: Lint passa sem erros

### Novo arquivo: `src/lib/ecdh.ts`

```ts
// Gera keypair X25519 por sessão (in-memory)
export async function generateSessionKeypair(): Promise<CryptoKeyPair> {
  return crypto.subtle.generateKey({ name: 'X25519' }, false, ['deriveKey'])
}

// Exporta chave pública como base64 para envio ao servidor
export async function exportPubKey(pubKey: CryptoKey): Promise<string> {
  const raw = await crypto.subtle.exportKey('raw', pubKey)
  return btoa(String.fromCharCode(...new Uint8Array(raw)))
}

// Importa chave pública de base64
export async function importPubKey(b64: string): Promise<CryptoKey> {
  const raw = Uint8Array.from(atob(b64), c => c.charCodeAt(0))
  return crypto.subtle.importKey('raw', raw, { name: 'X25519' }, true, [])
}

// Deriva AES-256-GCM a partir do shared secret ECDH
export async function deriveSharedKey(privKey: CryptoKey, peerPubKey: CryptoKey): Promise<CryptoKey> {
  return crypto.subtle.deriveKey(
    { name: 'X25519', public: peerPubKey },
    privKey,
    { name: 'AES-GCM', length: 256 },
    false,
    ['encrypt', 'decrypt']
  )
}

// Gera roomKey aleatória (AES-256-GCM)
export async function generateRoomKey(): Promise<CryptoKey> {
  return crypto.subtle.generateKey({ name: 'AES-GCM', length: 256 }, true, ['encrypt', 'decrypt'])
}

// Exporta roomKey para cifrar com shared secret (para distribuição)
export async function exportRoomKey(roomKey: CryptoKey): Promise<ArrayBuffer> {
  return crypto.subtle.exportKey('raw', roomKey)
}

// Importa roomKey decifrada
export async function importRoomKey(raw: ArrayBuffer): Promise<CryptoKey> {
  return crypto.subtle.importKey('raw', raw, { name: 'AES-GCM', length: 256 }, false, ['encrypt', 'decrypt'])
}
```

### Modificações em `src/lib/socket-client.ts`

```ts
// Adicionar refs:
const keypairRef = useRef<CryptoKeyPair | null>(null)
const roomKeyRef = useRef<CryptoKey | null>(null)  // substitui keyRef
const pendingMessagesRef = useRef<Array<() => void>>([])

// No init(), antes de conectar:
keypairRef.current = await generateSessionKeypair()
const pubKeyB64 = await exportPubKey(keypairRef.current.publicKey)

// Após socket.on('connect'):
socket.emit('key-exchange', { roomId, pubKey: pubKeyB64 })

// Handler de peer-pubkey (participante existente recebe novo entrante):
socket.on('peer-pubkey', async ({ socketId, pubKey }) => {
  if (!roomKeyRef.current || !keypairRef.current) return
  const peerKey = await importPubKey(pubKey)
  const sharedKey = await deriveSharedKey(keypairRef.current.privateKey, peerKey)
  const roomKeyRaw = await exportRoomKey(roomKeyRef.current)
  const { ciphertext, iv } = await encryptRoomKey(sharedKey, roomKeyRaw) // usa encryptBinary
  socket.emit('room-key-offer', { roomId, targetSocketId: socketId, encryptedRoomKey: ciphertext, iv, senderPubKey: pubKeyB64 })
})

// Handler de room-key-offer (novo participante recebe chave):
socket.on('room-key-offer', async ({ encryptedRoomKey, iv, senderPubKey }) => {
  if (roomKeyRef.current) return // já tem a chave
  const senderKey = await importPubKey(senderPubKey)
  const sharedKey = await deriveSharedKey(keypairRef.current!.privateKey, senderKey)
  const roomKeyRaw = await decryptRoomKey(sharedKey, encryptedRoomKey, iv) // usa decryptBinary
  roomKeyRef.current = await importRoomKey(roomKeyRaw)
  // Flush pending messages
  pendingMessagesRef.current.forEach(fn => fn())
  pendingMessagesRef.current = []
})
```

**Timeout de 5s** (AC12): se `roomKeyRef.current` ainda for null após 5s do connect, gera uma nova `roomKey` própria.

**Enfileiramento** (AC13): `sendMessage` verifica `if (!roomKeyRef.current)` e em vez de retornar, empurra para `pendingMessagesRef`.

### Modificações em `server.ts`

```ts
// Map de pubKeys por sala (socketId → pubKey)
const roomPubKeys = new Map<string, Map<string, string>>() // roomId → (socketId → pubKey)

socket.on('key-exchange', ({ roomId, pubKey }) => {
  // Registrar pubKey deste socket
  if (!roomPubKeys.has(roomId)) roomPubKeys.set(roomId, new Map())
  roomPubKeys.get(roomId)!.set(socket.id, pubKey)

  // Enviar pubKeys existentes para o novo entrante
  roomPubKeys.get(roomId)!.forEach((existingPubKey, existingSocketId) => {
    if (existingSocketId === socket.id) return
    socket.emit('peer-pubkey', { socketId: existingSocketId, pubKey: existingPubKey })
  })

  // Anunciar novo entrante para os existentes
  socket.to(roomId).emit('peer-pubkey', { socketId: socket.id, pubKey })
})

socket.on('room-key-offer', ({ roomId, targetSocketId, encryptedRoomKey, iv, senderPubKey }) => {
  // Relay direto para o socket destino
  io.to(targetSocketId).emit('room-key-offer', { encryptedRoomKey, iv, senderPubKey })
})

// No disconnect/leave: limpar pubKeys
socket.on('disconnecting', () => {
  for (const roomId of socket.rooms) {
    roomPubKeys.get(roomId)?.delete(socket.id)
  }
})
```
