# Story 1.11 — Auto-Destruição com Master Password

**Status:** Ready
**Epic:** 1 — IcognitoChat MVP
**Story:** 1.11
**Depende de:** 1.2, 1.7, 1.9, 1.10

---

## Descrição

Como administrador do servidor, quero poder acionar um comando de auto-destruição autenticado pelo master password que apague imediatamente todos os usuários, salas e dados do banco, desconecte todos os participantes ativos e torne o servidor inacessível até que novos usuários sejam criados — para garantir controle total sobre o ciclo de vida dos dados em situações de emergência ou encerramento.

---

## Contexto Técnico

### O que é destruído

| Dado | Localização | Ação |
|------|-------------|------|
| Usuários (credenciais) | SQLite `users` | `DELETE FROM users` |
| Salas (persistentes + efêmeras) | SQLite `rooms` | `DELETE FROM rooms` |
| Mensagens | SQLite `messages` | `DELETE FROM messages` (ON DELETE CASCADE) |
| Conexões ativas | Socket.io in-memory | Emit `server-destroyed` → todos redirecionados |
| Estado in-memory | `roomUsers`, `roomOwners`, `ephemeralRooms` | Cleanup natural via `disconnect` handler existente |
| Sessões (iron-session) | Stateless — sem store central | Invalidas naturalmente: userId deletado → próxima request autenticada falha |

### Por que truncar tabelas e não deletar o arquivo DB

Deletar o arquivo SQLite no Railway Volume causaria crash do servidor na próxima request. Truncar as tabelas mantém o servidor rodando mas completamente vazio — novo usuário pode ser criado imediatamente. O arquivo do volume é preservado; os dados não.

### Rate Limiting obrigatório

Endpoint de destruição irreversível exige proteção contra uso acidental ou tentativas automatizadas. Implementado com utilitário in-memory (Map no processo Node.js) — adequado para instância única no Railway sem dependência externa (Redis, Upstash, etc.).

**Política:**
- Janela: 15 minutos
- Máximo: 3 tentativas por IP (incluindo chamadas bem-sucedidas)
- Resposta ao bloquear: `429 Too Many Requests` + header `Retry-After` (segundos)
- Chave: IP extraído de `x-forwarded-for` ou `req.ip`

## Critérios de Aceitação

- [ ] `POST /api/auth/admin/destroy` autenticado via header `x-master-password` retorna `401` se senha inválida
- [ ] Endpoint aplica rate limit: máximo 3 tentativas por IP em janela de 15 minutos; exceder retorna `429` com header `Retry-After`
- [ ] Ao ser acionado com sucesso: todos os registros de `users`, `rooms` e `messages` são deletados do banco
- [ ] A sala "Geral" **não** é re-criada automaticamente após a destruição (estado de destruição total)
- [ ] Todos os sockets conectados recebem evento `server-destroyed` antes da limpeza do banco
- [ ] Usuários em salas de chat são redirecionados para `/` com mensagem "O servidor foi encerrado pelo administrador"
- [ ] A resposta de sucesso retorna um resumo: `{ destroyed: { users, rooms, connections } }`
- [ ] O servidor continua rodando após a destruição (não encerra o processo)
- [ ] Usuários no hub `/chat` que não recebem o evento socket são redirecionados para `/` na próxima navegação (sessão inválida — usuário deletado)
- [ ] `src/lib/rate-limit.ts` é um utilitário genérico reutilizável para outras rotas admin futuras

## Notas de Implementação

```typescript
// src/lib/rate-limit.ts
const store = new Map<string, { count: number; resetAt: number }>()

export const DESTROY_LIMIT = { max: 3, windowMs: 15 * 60 * 1000 }

export function checkRateLimit(
  ip: string,
  max: number,
  windowMs: number
): { allowed: boolean; retryAfter?: number } {
  const now = Date.now()
  const entry = store.get(ip)

  if (!entry || now > entry.resetAt) {
    store.set(ip, { count: 1, resetAt: now + windowMs })
    return { allowed: true }
  }

  if (entry.count >= max) {
    return { allowed: false, retryAfter: Math.ceil((entry.resetAt - now) / 1000) }
  }

  entry.count++
  return { allowed: true }
}
```

```typescript
// src/lib/db.ts — nova função
export function destroyAllData(): { users: number; rooms: number } {
  const result = db.transaction(() => {
    db.prepare('DELETE FROM messages').run()
    const rooms = db.prepare('DELETE FROM rooms').run()
    const users = db.prepare('DELETE FROM users').run()
    return { users: users.changes, rooms: rooms.changes }
  })()
  return result
}
```

```typescript
// src/app/api/auth/admin/destroy/route.ts
import { NextRequest, NextResponse } from 'next/server'
import { checkRateLimit, DESTROY_LIMIT } from '@/lib/rate-limit'
import { destroyAllData } from '@/lib/db'

export async function POST(req: NextRequest) {
  const ip = req.headers.get('x-forwarded-for')?.split(',')[0].trim() ?? 'unknown'

  const { allowed, retryAfter } = checkRateLimit(ip, DESTROY_LIMIT.max, DESTROY_LIMIT.windowMs)
  if (!allowed) {
    return NextResponse.json(
      { error: 'Muitas tentativas. Tente novamente mais tarde.' },
      { status: 429, headers: { 'Retry-After': String(retryAfter) } }
    )
  }

  const masterPassword = req.headers.get('x-master-password')
  if (!masterPassword || masterPassword !== process.env.MASTER_PASSWORD) {
    return NextResponse.json({ error: 'Não autorizado' }, { status: 401 })
  }

  const io = (global as any).io
  const connections = io?.engine?.clientsCount ?? 0
  io?.emit('server-destroyed')

  const { users, rooms } = destroyAllData()

  return NextResponse.json({ destroyed: { users, rooms, connections } })
}
```

### Uso via curl

```bash
curl -X POST https://seu-app.railway.app/api/auth/admin/destroy \
  -H "x-master-password: sua_senha_master"

# Resposta:
# { "destroyed": { "users": 5, "rooms": 3, "connections": 2 } }
```

### Comportamento pós-destruição

- Servidor continua rodando — nenhum dado persiste
- Próximo login de qualquer usuário falha (tabela `users` vazia)
- Para restaurar: `POST /api/auth/admin/users` cria novos usuários
- Sala "Geral" volta a existir no próximo restart do servidor (seed no `db.ts`)
