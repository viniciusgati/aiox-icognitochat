# Story 1.10 — Persistência de Usuários via Railway Volume

**Status:** Ready for Review
**Epic:** 1 — IcognitoChat MVP
**Story:** 1.10
**Depende de:** 1.1

---

## Descrição

Como usuário cadastrado, quero que minha conta e senha sejam preservadas entre deploys do servidor, para que eu não perca meu acesso toda vez que uma nova versão do app é publicada no Railway.

---

## Contexto Técnico

Atualmente o banco SQLite é gravado em `data/icognitochat.db` relativo ao `process.cwd()` — dentro do container Railway, que é destruído a cada deploy. Além disso, `zeroizeDb()` em `src/lib/db.ts` é chamada no SIGTERM (sinal enviado pelo Railway ao encerrar o container), apagando deliberadamente o banco antes do shutdown.

A solução é:

1. **Railway Volume** montado em um diretório fixo (ex: `/data`) — disco persistente que sobrevive a deploys.
2. **Variável de ambiente `DB_PATH`** apontando para o volume — permite configuração por ambiente (Railway usa o volume, local usa `./data`).
3. **Remover `zeroizeDb()` do handler de SIGTERM** — a limpeza era intencional para o modo "incógnito" mas conflita com persistência de usuários. O wipe de dados de chat (mensagens) pode continuar, mas credenciais de usuários devem ser preservadas.

### Separação: dados efêmeros vs dados persistentes

| Dado | Comportamento atual | Comportamento desejado |
|------|--------------------|-----------------------|
| `users` (credenciais) | Apagado no deploy | **Persistir** no Railway Volume |
| `rooms` permanentes | Apagado no deploy | **Persistir** no Railway Volume |
| `messages` | Apagado no deploy | Manter efêmero (apagar no shutdown é OK) |
| Salas efêmeras | Apagadas corretamente | Manter comportamento atual |

Como todos os dados estão no mesmo arquivo SQLite, a solução mais simples é persistir o arquivo inteiro e remover o `zeroizeDb()` do SIGTERM. O comportamento incógnito das mensagens é garantido pela natureza efêmera das salas (sem histórico persistente de mensagens por design).

## Critérios de Aceitação

- [ ] O path do banco SQLite é configurado via variável de ambiente `DB_PATH` (fallback: `./data/icognitochat.db` para desenvolvimento local)
- [ ] No Railway, `DB_PATH` aponta para o diretório do Volume montado (ex: `/data/icognitochat.db`)
- [ ] A função `zeroizeDb()` é removida do handler de SIGTERM em `server.ts` — o banco não é mais apagado em shutdowns normais de deploy
- [ ] `zeroizeDb()` e `secure-cleanup.ts` podem ser mantidos para uso explícito futuro (não deletar a função, apenas remover do SIGTERM)
- [ ] Usuários cadastrados persistem após um novo deploy no Railway
- [ ] Desenvolvimento local continua funcionando sem Railway Volume (usando path local)
- [ ] O `README` ou `.env.example` documenta a variável `DB_PATH` e as instruções de setup do Railway Volume

## Notas de Implementação

```typescript
// src/lib/db.ts — nova lógica de path
const DB_PATH = process.env.DB_PATH ?? path.join(process.cwd(), 'data', 'icognitochat.db')
const DATA_DIR = path.dirname(DB_PATH)

if (!fs.existsSync(DATA_DIR)) {
  fs.mkdirSync(DATA_DIR, { recursive: true })
}
```

```typescript
// server.ts — remover zeroizeDb() do shutdown
// ANTES:
process.on('SIGTERM', () => {
  zeroizeDb()  // ← REMOVER ESTA LINHA
  server.close(...)
})

// DEPOIS:
process.on('SIGTERM', () => {
  server.close(() => process.exit(0))
})
```
